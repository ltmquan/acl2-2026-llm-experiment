       Based on APL, Remora is a rank-polymorphic language designed to simplify the task of writing
       efﬁcient, GPU-aware code. As such, it avoids using iteration (including loops and recursion) by
       deﬁning a “lifting” mechanism that automatically runs a function that expects an argument of a
       given dimension over all matching parts of a higher-dimension argument. In simple cases, this is
       straightforward; e.g., calling abs on a vector performs an implicit map, so it returns a new vector
       with the absolute value of each of its elements. More generally, the exact mechanics of this lifting
       process are quite complicated, as they depend on all arguments to the function, which need only
       partially match in shape. In this paper, we describe a methodology that we follow to reason about the
       behavior of lifting primitive operations over compatible arguments.


1     Introduction
Remora is a recent modern programming language that intends to ﬁll a very speciﬁc niche. Based on
APL, it is a rank-polymorphic language designed to simplify the task of writing efﬁcient, GPU-aware
code. The programmer writes code that may beneﬁt from parallelization, and the compiler automatically
generates code that uses the GPU to perform the computation, including planning the data transfer be-
tween the CPU and GPU. As such, it makes some unusual design decisions, such as avoiding the use of
iteration—no loops, no recursion [3].
     In part, Remora avoids the use of iteration by supporting many of the standard higher-order functions,
such as map, reduce, and scan. Another trick up Remora’s sleeves is rank-polymorphism, which allows
functions to vary their behavior based on the shape of the arguments. The key concept is that all data
structures are n–dimensional arrays. A function expects to receive parameters of a given rank (also
known as dimension), but it can be called with an argument of higher rank, in which case the system
automatically “lifts” the function to operate on the higher–ranked arguments. I think of this is as an
implicit map operation, where Remora automatically uses map to run a scalar (rank-0) operation on a
vector (rank-1) argument.
     The semantics of lifting is further complicated by the fact that Remora functions allow for multiple
parameters, and the actual run-time semantics differs based on the shape of all of its arguments. For
example, when you add a vector and a matrix, the system automatically lifts the vector to a matrix by

2     The Real Semantics of Lifting
As mentioned above, Remora is a complicated language, involving different types of function application—
ordinary function application over values, but also application over the space of types, and another type
of application over indices. The molecules of Remora programs are cells, which can hold numbers,
booleans, and the like. Values, what variables1 in Remora programs actually store, are arrays of cells.
    More precisely, Remora arrays have a speciﬁc shape and rank. The rank corresponds to the number of
dimensions, e.g., a three-dimensional array requires three indexes to access a speciﬁc cell. Additionally,
a shape describes the size of each dimension. E.g., a vector is a rank-1 data structure, so it can be indexed
with a single index. The shape tells us how many cells it has in that direction. Thus, a 3-element vector
and a 10-element vector have the same rank, but different shape. The shape of an array is usually given
as a vector of natural numbers, and the rank is the length of that vector. For example, a 3x4 matrix has
shape [3 4] and rank 2. Scalars, the only types that can appear inside a Remora array, are considered to
be rank-0.
    Rank-polymorphism in Remora applies to differences in rank, not shape. For example, consider the
addition primitive operation. In Remora syntax, which superﬁcially resembles Lisp, we can write (+ 1

2) to add two scalars. Unsurprisingly, the result is 3.
     The same operator handles arguments of higher rank. For example, the vectors [1 2 3] and [4 5 6]
can be added element-wise to produce [5 7 9]. In this case, we are adding two rank-1 arrays with a
rank-0 operator. But the operator will not work on arguments of different shape, as opposed to rank. For
example, if you try to add the vectors [1 2 3] and [4 5], you will get a run-time error. The same will
happen if you try to add the vector [1 2 3 4] and the matrix [[1 2] [3 4]], even though they have the same
number of cells.
     The more interesting case is when the arguments have different, but compatible ranks. There are, of
course, important limitations. What should be the result of adding [1 2] and [[1 2] [3 4]]? Or how about
[1 2] and [[1 2] [[5 6]]]? The ﬁrst example works, and the result is [[2 3] [5 6]]. The second example, on
the other hand, does not work and instead produces a run-time error.
     The rule governing this behavior is as follows. The system starts by comparing the shapes of the
arguments. In the ﬁrst case, the shapes are [2] and [2 2]. The important think to notice is that [2] is a
preﬁx of [2 2]. For the second example, the shapes are [2] and [3 2]. In this case, neither shape is a preﬁx
of the other, so the system produces a run-time error.
     After determining that the shapes are compatible, the shape of the output can be determined. It is
simply the shape of the argument with the longer shape. In order to carry out the operation, Remora
seemingly lifts the shorter argument by copying it to match the shape of the longer one. This is best
understood in terms of indexing. Suppose the shorter argument has shape [10 5] and the larger one has
shape [10 5 3 4]. The shorter argument is lifted from rank-2 to rank-4, and the way this is done is by
returning the value in A[i, j] when asked for the value of A[i, j, k, l]. In other words, the shorter argument
is replicated along the extra dimensions.
     There are many other complications, but one in particular must be addressed. The semantics of
Remora use Currying for function application. So the computation of (+ 1 2) is actually performed in
multiple steps:
   1. First, the arguments are grouped into a single list, so we really have something like (+ (1 2)).
   2. Then, the function is applied to the ﬁrst argument, resulting in a new anonymous function that I
      call 1+ in homage to ACL2. We now have (1+ (2)).
   3. Next, the function 1+ is applied to the second argument, resulting in a new anonymous function
      that I call 3+. We now have (3+ ()).
   4. At this point, we are out of arguments, so the function returns the hidden argument in 3+, which is
      to say 3 as expected.
   To give a better idea of what’s going on, consider the example of adding the vectors [1 2] and [3 4].
The steps proceed as follows:
   1. (+ ([1 2] [3 4])), treating the operation as a function working on a list of (Curried) argu-
      ments.
   2. ([1+ 2+] ([3 4])), where the “function” is now a vector in its own right.
   3. ([4+ 6+] ()), where each function in the vector operates on it corresponding argument (and
      returns a function).
   4. [4 6], the ﬁnal answer.
You may have been surprised at the second step, where the function became an array of functions. This
is naturally permitted in Remora, as a higher-order language. When a function isn’t scalar, it is treated

     All of these details and more are handled by the ACL2 implementation of Remora. In the interest of
full disclosure, I had no part in that implementation; I am simply in awe of it. For my purpose, it serves
as the “gold standard” for the semantics of Remora, and I use it to reason about my Remora programs.
Technically, the proofs are not about Remora programs, but rather about what the ACL2 implementation
of Remora does when it evaluates those programs. This is all good, but it comes at a price. Even simple
Remora programs require reasoning about the details of the “gold standard” implementation, which has
to deal with all of the complications. This can be done, e.g., as in the PLT Redex project [1] or any
number of complicated hardware models in ACL2, but it is not easy.
     For the remaining of the paper, it is useful to have a very rough idea of the ACL2 implementation
of Remora. The relevant portion is a clique of mutually recursive functions that interpret a Remora
expression. The entry point is eval-expr, which looks at an expression and dispatches execution to
a specialized member of the clique. For function applications, including built-in functions, it calls the
function eval-app, which manages the entire process including the Currying loop described above.
At each iteration, eval-loop calls eval-app-list, which evaluates a function vector on a vector of
arguments. The result is a vector, which is then repackaged by eval-app into the appropriate shape.

4    Equivalent Expressions in ACL2
While the previous sections described the work we’ve done for the past year, this section describes work
that we’re wrapping up right now. Our original plan was that we could deﬁne the semantics of Remora
programs by providing an equivalent ACL2 function. We abandoned that approach because it doesn’t
appear feasible, but after doing the work described in the previous sections, we changed our mind and
started experimenting.
     The key idea is related to the “glue” theorems described above. But in this case, the round trip is to
an ACL2 list of lists, as opposed to a single ﬂat list. The ACL2 lists hold ACL2 objects instead of the
Remora cells, so functions on those data structures are POAL, as in Plain Old ACL2 Lists.
     We have a pair of encoder/decoder functions that convert from Remora vectors to ACL2 nested lists.
We also have a ﬂattener that takes a nested list and turns into a linear list of cells and back. What’s
missing is the connection between that linear list and the one used between steps in the β -reduction.
That will establish the commutative diagram that shows you can execute the Remora program or convert
the arguments to ACL2 lists, run the equivalent ACL2 program on lists, then convert the result back to
Remora—and end up with the same answer as the original Remora program. Another way to look at this
is to use the ACL2 program as a speciﬁcation for the Remora program, and end up with a proof that the
Remora program meets that speciﬁcation, but obviously much faster.
     The most interesting part of the project is the function nested-map that takes as arguments a “func-
tion” and its arguments. Right now, the function argument is an ACL2 identiﬁer that is used to look up
one of the built-in functions in a table. After all, ACL2 is not higher-order. But the other arguments can
be arbitrary nested lists, as long as they are compatible. The result is a new rested list of the appropriate
shape. The ongoing work is to prove this function returns the same shape that the Remora semantics
expects.

   To be clear, this will not work for all Remora programs, but it will work with many of the existing
examples. In particular, we’re hoping it will enable us to formalize the Darknet example.


5    Conclusion
Novel programming languages come and go, but the Remora language is especially interesting, because
of its signiﬁcant potential for GPU programming. As the Darknet example shows, they are focused on
AI applications, more so than on traditional scientiﬁc computing—though it could obviously be used for
that as well.
     We have been working on building a methodology to reason about the correctness of Remora pro-
grams, without sacriﬁcing the relative ease of reasoning about pure Lisp functions. In the future, we
plan to cover more and more of the language semantics. Particularly lacking right now is any thought
of supporting user-deﬁned functions, so that is our next step. That will present a challenge, because the
Remora semantics allows a function to specify the shape of its input arguments. The current code expects
function to work only on scalars, so that is a signiﬁcant simpliﬁcation.
     After that, we hope to work on formalizing signiﬁcant Remora examples, like the Darknet showcase.

# An executable MIR semantics in ACL2, running RustCrypto's fixsliced AES-128

This directory holds the third artifact of the paper (Section 6): an
executable semantics of a subset of Rust's MIR as ACL2 fixtypes and an
interpreter, an importer for Charon's ULLBC JSON, and the paper's AES subject
run on it.  It was written from the paper's description; the authors'
implementation was not used.

## Layout

| Path | Contents |
|---|---|
| `subject/` | Cargo crate `aes_fixslice`: AES-128-only adaptation of `aes` 0.9.1 `src/soft/fixslice32.rs` (`src/lib.rs`), FIPS-197 cargo tests (`tests/fips197.rs`) |
| `subject/fixslice32.upstream.rs` | Pristine upstream file, for diffing |
| `subject/ADAPTATION.md` | Every difference from upstream |
| `subject/AUDIT.txt` | Output of `scripts/audit.py`, the item-by-item audit |
| `subject/aes_fixslice.ullbc` | Charon's ULLBC JSON for the crate (`--mir elaborated`) |
| `mir/syntax.lisp` | Fixtypes for the MIR subset: integer types, types, constants, places and projections, operands, rvalues, statements, terminators, blocks, bodies, programs |
| `mir/values.lisp` | Fixtypes for runtime values, locations (pointers), frames, machine states, and memory reads/writes |
| `mir/stdlib.lisp` | Integer operations (including the overflow-checked forms) and the 33 standard-library models |
| `mir/interpreter.lisp` | The interpreter: big-step places, operands, and rvalues; small-step statements and terminators; `run`, globals, `call-function` |
| `mir/import-json.lisp` | The importer: sharing expansion, JSON-to-fixtype mapping, classifier |
| `mir/aes-program.lisp` | The program fixture `*aes-program*` (generated by `mir/gen-program.sh`) |
| `mir/import-test.lisp` | Import test: parses the JSON during certification and checks the result equals `*aes-program*` |
| `run.lisp` | `mir-aes-encrypt`, `mir-aes-decrypt`, the FIPS-197 tests, and the differential tests |
| `scripts/adapt.py` | Builds `subject/src/lib.rs` from the upstream file |
| `scripts/audit.py` | Whitespace- and comment-insensitive item-by-item audit |
| `scripts/expand.py` | Python reference model of the importer's sharing expansion (a development aid) |

All the ACL2 code is in logic mode, and its guards are verified, so it runs as
compiled Lisp.  There is no `skip-proofs`, `defaxiom`, trust tag, or
redefinition.

## Commands

Producing the ULLBC JSON (Charon 0.1.315 and its toolchain, as installed). Run
in `subject/`:

    charon cargo --ullbc --mir elaborated --dest-file aes_fixslice.ullbc

This is Charon without monomorphization or any of the extraction pipeline's
reshaping flags, on the runtime-phase MIR (`--mir elaborated`, after drop
elaboration), as in Section 6.2.  The output is deterministic: running it
again gives the same file byte for byte.

Running the crate's own tests (in `subject/`): `cargo test --offline`.

Regenerating the adaptation and the audit (in `/work`):

    python3 scripts/adapt.py subject/fixslice32.upstream.rs subject/src/lib.rs
    python3 scripts/audit.py subject/fixslice32.upstream.rs subject/src/lib.rs > subject/AUDIT.txt

Regenerating the program fixture after the JSON changes (needs
`mir/import-json` certified): `mir/gen-program.sh`.

Certifying everything (in `/work`):

    cert.pl -j4 mir/*.lisp run.lisp

This takes about two minutes. `run.lisp` takes about a minute of that,
running about 200 interpreted encryptions and decryptions.

Using the entry points:

    (include-book "/work/run")
    (mir-aes-encrypt key block)   ; key, block: lists of 16 bytes (aes::inp)
    (mir-aes-decrypt key block)

They take and return keys and blocks in the same representation as
`aes::aes-128-encrypt` and `aes::aes-128-decrypt`
(`kestrel/crypto/aes/aes-spec`). Note the argument order: the key comes
first, as in the Rust entry points, while the spec functions take the block
first. So `(mir-aes-encrypt k b)` is compared against
`(aes::aes-128-encrypt b k)`. If the interpreted run panics or fails, the
result is `(:mir-failure outcome)`. For example, a key that is not 16 bytes
long fails one of the crate's `debug_assert_eq!`s.

## The semantics (Section 6.1)

* **Values** are structured, not bytes: typed integers, booleans, ADT
  values (structs, tuples, enum variants), arrays, pointers, strings, plus
  models of the opaque iterator types: slice `Iter`/`IterMut`, `StepBy`,
  `Rev`, and `Zip`.
* **A pointer** is a location: a base (a frame's local, numbered from the
  bottom of the stack; a global; or a static allocation) and a path of
  field, index, and slice-window steps. A slice reference is a pointer to an
  array or to a window of one. `p.metadata` (`PtrMetadata`) is the length of
  the designated slice.
* **The interpreter** takes small steps at the statement and terminator
  level: one step per statement, and one per terminator, a call to a
  modeled standard-library function included. Places, operands, and rvalues
  are evaluated big-step.
* **Terminators:** Goto, SwitchInt (Charon's `Switch`), Call, Assert,
  Return, Unreachable (Charon's `UndefinedBehavior`), and Abort (also used
  for Charon's `UnwindResume`, which can only be reached through unwind
  edges).
* **Statements:** Assign, StorageLive, StorageDead (and Nop).
* **Eight rvalue forms:** Use, Ref, RawPtr, BinaryOp, UnaryOp (`!`, `-`,
  integer casts, unsizing), Discriminant, Aggregate, and Repeat.
* **Sixteen binary operators:** `+ - * / % ^ & | << >> == != < <= > >=`.
  Each has a wrap, panic, or UB overflow mode. rustc's default overflow
  checks reach the interpreter as calls to the `add/sub/mul_with_overflow`
  intrinsics followed by an Assert.
* **33 standard-library models**, of which the AES program calls 27. These
  cover:
  * slice `len`
  * `Index`/`IndexMut` on arrays and slices, by `usize`, `Range`,
    `RangeTo`, `RangeFrom`, and `RangeFull`, with core's bounds panics. The
    model is chosen per call site from the call's generic index type.
  * `copy_from_slice`
  * the `TryInto` slice-to-array conversion and `Result::unwrap`
  * `[T; N]::default`
  * `u32::from_le_bytes`, `to_le_bytes`, `rotate_right`, and `rotate_left`
  * `BitXorAssign<&u32>`
  * the overflow intrinsics
  * `iter`, `iter_mut`, and `IntoIterator`: the identity on iterators, and
    the conversion a slice reference undergoes inside `zip`
  * `next` for `Range`, `StepBy`, `Rev`, slice iterators, and `Zip`, plus
    `next_back`
  * `step_by`, `rev`, and `zip`
  * the two panic entry points, `panic` and `assert_failed`
* **Operating assumptions:**
  * a 64-bit target (`usize` is 64 bits; the importer checks the target's
    pointer size)
  * abort on panic: unwind edges are dropped at import, and a panic ends
    the run with a `:panic` outcome
  * moves read without de-initializing
  * drops are no-ops (the importer rejects `Drop`; the crate's MIR has
    none)
  * an enum's discriminant is its variant index (the importer rejects a
    `Discriminant` read of any enum for which this is false)
* **Globals.** Promoted constants are evaluated before a call by running
  their initializer bodies. A returned pointer into the initializer's own
  frame is moved to a static allocation.

## The importer (Section 6.2)

1. **Sharing expansion.** Charon writes each hash-consed value
   (types, trait references, constant expressions, layout size expressions,
   layout predicates, and spans) in full at its first occurrence as
   `{"Value": [id, X]}`, then refers to it by `{"Deduplicated": id}`. An
   unshared occurrence is written `{"Untagged": X}`. There is one id space
   per table. The importer tells which table a marker belongs to from the
   JSON context: the field name, the list position, and the sibling fields
   (`jx-category`). It expands the 40,615 markers in the AES dump (7,032
   `Value`, 33,224 `Deduplicated`, 359 `Untagged`) and drops spans.
   * The rules were validated against Charon's unshared serialization
     (`--no-dedup-serialized-ast`, 13 MB). Importing that dump gives a
     program `equal` to the one imported from the shared dump, and the
     Python reference expansion gives JSON identical to it.
2. **Mapping to the fixtypes.** The importer uses nil-tolerant navigation
   functions (`jget`, `jelem`, `jtag`, ...). ACL2 accepts their recursion
   over the semi-structured input after a handful of linear `acl2-count`
   lemmas.
3. **Classifier.**
   * Crate functions are named by identifier, for example
     `aes_fixslice::encrypt`.
   * Standard-library declarations are named by a path that renders
     implementations by trait and self type, for example
     `core::array::{impl core::ops::index::Index for array}::index`. A table
     maps these paths to models.
   * Because nothing is monomorphized, the model is completed per call site
     from the call's generic arguments: the `Index` flavor, the `TryInto`
     target array type, and the substituted self type `[u32; 8]` for
     `Default`.

Importing the 4.2 MB JSON (parse, expand, and map) takes about 0.5 s. The
result has 52 functions (40 of the crate and 12 promoted-constant
initializers) and 13 globals. `mir/import-test.lisp` re-imports the JSON
during certification and checks that the result equals `*aes-program*`.

## Running AES (Section 6.3)

* One interpreted encryption takes 76,954 machine steps, and one
  decryption takes 80,330. Each takes about 0.3 s (including evaluating
  the globals).
* `run.lisp` checks by execution, with `assert-event`:
  * The FIPS-197 Appendix C.1 and Appendix B ciphertexts, byte for byte,
    and decryption inverting both.
  * 66 differential inputs, `mir-aes-encrypt` against
    `aes::aes-128-encrypt`. Two are corner cases (all-zero and all-`0xff`
    key and block); 64 are pseudorandom key/block pairs generated in-book
    by a xorshift generator.
  * Decryption inverts the pseudorandom ciphertexts.
  * Beyond the paper, `mir-aes-decrypt` also agrees with
    `aes::aes-128-decrypt` on the same 66 inputs.

## Differences from the paper's description

These come from the toolchain installed here, Charon 0.1.315 upstream:

* **Panics.** Charon emits calls to the panic entry points as Call
  terminators whose continuation is `UndefinedBehavior`, not as `Abort`
  terminators. The two panic functions are therefore modeled (as panics)
  and called.
* **Overflow checks.** Checked arithmetic arrives as the
  `*_with_overflow` intrinsics, which are modeled, rather than as
  checked-binop rvalue forms.
* **Different numbers.** The JSON is 4.2 MB rather than 6.9 MB, the marker
  count is 40,615 rather than 19,249, and the program calls 27 models
  rather than 23.
